# Direct3D 8

Madeira answers `d3d8.dll` in the 32-bit (i386) runtime with
[d3d8to9](https://github.com/crosire/d3d8to9) (BSD-2-Clause), which implements
Direct3D 8 on the public Direct3D 9 interfaces. On Madeira, Direct3D 9 is
DXMT's (Metal), so a Direct3D 8 game runs as:

```
game -> d3d8.dll (third_party/d3d8to9) -> d3d9.dll (DXMT) -> Metal
```

## Why this was needed

Wine's own `d3d8.dll` is a frontend over `wined3d`, and its `Direct3DCreate8`
calls `wined3d_create` with no fallback. `wined3d` has no backend on iOS (no
OpenGL, and Madeira does not require Vulkan), so before this change
`Direct3DCreate8` returned `NULL` and every Direct3D 8 game stopped at start-up.

## Why not D8VK (Winlator's choice)

Winlator extracts `dxwrapper/d8vk-1.0.tzst` when the DXVK wrapper is selected.
D8VK (now DXVK's `src/d3d8`) talks to DXVK's own Direct3D 9 through private
bridge interfaces (`IDxvkD3D8Bridge`), so it needs DXVK's d3d9, i.e. Vulkan.
d3d8to9 needs nothing beyond `IDirect3D9` / `IDirect3DDevice9`, which DXMT's
`d3d9.dll` implements.

## What Madeira changed in d3d8to9

Listed file by file in `third_party/d3d8to9/MADEIRA_CHANGES.md`. In short:

- Shaders are translated at the token level (`madeira_d3d8_shader.hpp`)
  instead of upstream's D3DX disassemble / regex / reassemble path, which
  targets Microsoft's D3DX text format and Microsoft's validator. Wine's D3DX
  prints a different format, and DXMT's DXSO frontend reads SM1 bytecode
  directly. vs.1.0/1.1 gets one `dcl_<usage> v#` per input of the D3D8
  declaration; ps.1.0-1.4 is passed through (1.0 -> 1.1).
- Declaration constants (`D3DVSD_CONST`) are loaded when the shader is set,
  as in D3D8, instead of being baked into the shader.
- `GetVertexShaderDeclaration` works; the shader getters return the
  application's D3D8 tokens.
- No message box when `d3dx9_43.dll` is missing; a `[d3d8to9] ...` line goes
  to the session log instead, and `app/Madeira/LaunchDiagnostics.c`
  classifies those lines (graphics API, device, shader, dependency).

## Build and packaging

`build/d3d8/build.sh` compiles it with llvm-mingw (i686), statically links
the C++ runtime, marks the DLL as a Wine builtin with `winebuild --builtin`
(like DXMT's `d3d9.dll`) and copies it to `app/Madeira/i386-windows/`.
`build/wine-i386/build.sh` skips Wine's `d3d8.dll` and calls that script after
installing DXMT. A `d3d8.dll` the game ships in its own directory still loads
first (native before builtin), as on Windows.

There is no 64-bit `d3d8.dll`. Windows never had one, and the 64-bit farm does
not list it (`compat/wine-modules.json`, `wine_not_in_64bit_farm`).

## Tests (host, no iPad)

| Test | What it shows |
|---|---|
| `build/host-tests/check-d3d8-shader.py` | The translator, compiled with ASan/UBSan, produces vs_1_1 / ps_1_x that DXMT's own DXSO header parser and instruction walker (`research/dxmt/src/airconv/dxso_*.hpp`) accept; truncated, unknown-opcode and SM2+ input is refused. |
| `build/host-tests/check-d3d8to9-wine.py` | The DLL `build/d3d8/build.sh` produces, placed in a copy of an installed WoW64 Wine's `lib/wine/i386-windows` (as Madeira's farm does), is the `d3d8.dll` a 32-bit program gets; Direct3DCreate8 -> CreateDevice -> Clear/BeginScene/EndScene/Present, vertex shader with declaration and constant, pixel shader, getters, vs_2_0 refusal, and "no Direct3D 9" are checked against a recording `d3d9.dll` generated from the toolchain's `d3d9.h`. Needs `LLVM_MINGW`, `HOST_WINE`, `WINEBUILD`; prints SKIP otherwise. |
| `build/host-tests/check-launch-diagnostics.py` | The `[d3d8to9]` lines become the right launch-diagnostic stages and categories. |
| `build/host-tests/check-game-compat.py` | `d3d8` is "builtin" for 32-bit programs and missing for 64-bit ones. |

Finding from the Wine test: a builtin-marked `d3d8.dll` dropped next to the
`.exe` with `WINEDLLOVERRIDES=d3d8=n` is refused by Wine's loader
(`c0000135`); it must be in the builtin directory, which is where the build
puts it.

## Needs an iPad / Xcode (not done here)

- Rendering: nothing here has drawn through DXMT. The Wine test uses a
  recording Direct3D 9; the shader test uses DXMT's parser, not its Metal code
  generator. Whether DXMT's d3d9 renders what d3d8to9 asks for (fixed-function
  state, palettized textures, `CopyRects` format conversions) needs a device.
- The i386 farm with this DLL has not been built on macOS with
  `build/wine-i386/build.sh` and packaged by Xcode; only the script's syntax
  and the DLL build step were run on Linux.
- `d3dx9_43.dll` is needed only for `CopyRects` between different formats; if
  the farm does not provide it, that call fails and is logged.
